The price is written in SQL, not in JavaScript.

Express only moves numbers in and out. Every recalculation is a stored procedure call inside MySQL, so the same rules apply whether the storefront, a script, or an admin panel touches the row.

01 / request

A visit lands

The storefront pings POST /api/products/:id/view when a product page opens.

02 / write

Counter increments

UPDATE Products SET views_count = views_count + 1 — one row, no reads.

03 / recompute

Procedure runs

CALL UpdateDynamicPrices() rewrites current_price for every product at once.

04 / read

New price serves

GET /api/products returns the row as-is — the API has no pricing logic to drift.

Four rules, two hard limits.

The engine is deliberately boring: three linear signals on top of the base price, then a clamp so a runaway counter can never produce an absurd listing.

Three endpoints. No pricing code.

Run the backend on port 5001 and the Vite storefront on 5174 — the API surface is this small.

GET /api/products

Returns every row from Products including current_price, stock_quantity, views_count and sold_count.

[
  { "product_id": 3, "name": "Ultra-Slim 4K Monitor",
    "base_price": 399.5, "current_price": 420.0,
    "stock_quantity": 15, "views_count": 300, "sold_count": 45 }
]
POST /api/products/:id/view

Increments the view counter, then forces CALL UpdateDynamicPrices() so the next read shows the new price. Returns 404 if the product does not exist.

{ "message": "View count incremented successfully" }
POST /api/checkout

Body { "productId": 3, "quantity": 2 }. Runs inside a transaction: reads the price, rejects insufficient stock, writes the order, then recomputes prices.

{ "error": "Insufficient stock" }        // 400, transaction rolled back

The simulator above mirrors the formula in the project README. The stored procedure in MySQL remains the source of truth — if the two ever disagree, the database wins.
